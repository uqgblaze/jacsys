# Product Requirements Document: JacSYS

**Project name:** JacSYS  
**Expanded name:** Jac System  
**GitHub organisation:** `uq-course-profiles`  
**Status:** Proposed ecosystem consolidation and redesign  
**Primary implementation agent:** Codex  
**Primary deployment environments:** GitHub Pages, GitHub Actions, UQ Cloud, Raspberry Pi  
**Language:** Australian English

---

# 1. Executive Summary

JacSYS is an ecosystem for collecting, managing, publishing and consuming publicly available University of Queensland course and programme information.

The system should consolidate successful functionality from the existing:

- `uq-course-profiles/jacson`
- `uqgblaze/uqbs-course-profiles`

projects while introducing clearly separated deployment and responsibility boundaries.

JacSYS consists of the following products and repositories:

| Repository / product | Purpose |
|---|---|
| **JacSYS** | Ecosystem landing page, architecture and documentation. |
| **API** | Generated, versioned static API containing JacSON and indexSON files. |
| **JacMIN** | Server-side administration, scraping, data management, overrides, scheduling, validation and API publishing. |
| **JacDASH** | Human-readable browser and exploration interface for the API. |
| **JacBLACK** | Blackboard / Learn.UQ integration and presentation layer. |
| **JacXEL** | Planned Microsoft Excel add-in consuming the API. |

Two named data products are generated by JacMIN and published through the API:

**JacSON**  
JSON files representing individual UQ JAC/course profiles.

**indexSON**  
JSON index and grouping files describing courses, programmes, plans, schools, faculties, semesters and relationships between those entities.

The central architectural principle is:

> **JacMIN builds and manages the static API. JacSON describes individual course profiles. indexSON describes collections and relationships. JacDASH, JacBLACK and JacXEL consume the API.**

# 3. Repository Responsibilities

## 3.1 `uq-course-profiles/jacsys`

JacSYS is the front door to the ecosystem.

It should contain:

- ecosystem overview;
- architecture diagrams;
- terminology;
- links to all repositories;
- API documentation;
- deployment overview;
- development/contribution guidance;
- compatibility information;
- roadmap.

It may be deployed as a simple GitHub Pages site.

JacSYS should not contain production scraper logic or generated datasets.

---

## 3.2 `uq-course-profiles/api`

The API repository is the **generated public static API**.

It contains:

- JacSON files;
- indexSON files;
- schemas;
- build metadata;
- API version metadata.

It should contain little or no manually maintained application code.

Generated files must clearly state that they should not be edited directly.

Canonical changes must occur through JacMIN.

---

## 3.3 `uq-course-profiles/jacmin`

JacMIN is the **producer and administrative system**.

JacMIN is responsible for:

- scraping UQ JAC/course profiles;
- scraping UQ programme/catalogue information;
- normalising source data;
- validating data;
- managing automatic and manually overridden records;
- creating JacSON;
- creating indexSON;
- scheduling processing;
- monitoring jobs;
- comparing changes;
- publishing versioned API output;
- maintaining provenance;
- managing administrators through a browser interface.

JacMIN should deploy to:

- UQ Cloud;
- Raspberry Pi;
- suitable Linux servers.

---

## 3.4 `uq-course-profiles/jacdash`

JacDASH is the human-readable web interface.

It consumes only the static API.

It should provide:

- course browsing;
- searching;
- filtering;
- profile viewing;
- programme navigation;
- faculty/school navigation;
- comparisons;
- download/export functions;
- UQBS-specific overlays where available.

JacDASH must not rely on JacMIN being online.

---

## 3.5 `uq-course-profiles/jacblack`

JacBLACK is the Blackboard / Learn.UQ integration layer.

It consumes the versioned API and transforms relevant data into Blackboard-compatible presentation.

It may support:

- dynamically embedded content;
- generated static Blackboard content;
- reusable components;
- accessible UQ-styled output.

JacBLACK must not scrape UQ source systems directly.

---

## 3.6 `uq-course-profiles/jacxel`

JacXEL is the planned Microsoft Excel add-in.

It should eventually provide functions such as:

```excel
=JACXEL.TITLE("MGTS1301")

=JACXEL.GET("MGTS1301","course.title")

=JACXEL.CLOS("MGTS1301")

=JACXEL.ASSESSMENTS("MGTS1301")

=JACXEL.PROGRAMS("MGTS1301")
```

JacXEL is not required for the initial JacSYS release.

# 5. Static API Versioning

API versioning is a fundamental requirement.

Consumers must be able to remain pinned to a known data contract indefinitely.

For example, a Blackboard course delivered in 2025 may continue using API v2 even after JacSYS introduces API v3.

A schema change must therefore **not automatically break existing JacBLACK content, spreadsheets or other integrations**.

# 7. API Version Behaviour

An API version represents a **data contract**, not merely a software release.

Therefore:

- API v2 data must continue conforming to the v2 schema.
- API v3 may introduce breaking schema changes.
- publishing v3 must not overwrite v2;
- consumers may explicitly request their supported API version;
- old API versions may continue receiving compatible data where technically appropriate;
- historical course profiles should remain available under their original supported API contracts.

JacBLACK content inserted into a 2025 Blackboard course should therefore be able to continue requesting:

```text
/api/v2/...
```

even after v3 becomes current.

# 9. JacSON Definition

JacSON represents **individual UQ JAC/course profiles**.

One JacSON file should correspond to a specific published course offering/profile.

Example:

```text
/v2/profiles/7660/MGTS2301-62448-7660.json
```

JacSON contains detailed course-profile data such as:

- course code;
- course title;
- class code;
- semester;
- study period;
- location;
- attendance mode;
- units;
- school;
- faculty;
- coordinating unit;
- description;
- aims;
- requirements;
- learning outcomes;
- assessments;
- assessment-to-learning-outcome relationships;
- learning activities;
- staff;
- resources;
- timetable;
- source URL;
- provenance.

JacSON does not contain programme grouping logic unless that information is intrinsic to the individual profile.

# 11. indexSON Definition

indexSON consists of JSON files representing:

- collections;
- groupings;
- discovery information;
- structural relationships;
- navigation metadata.

indexSON may describe:

- courses;
- programmes;
- plans;
- majors;
- schools;
- faculties;
- semesters;
- offerings;
- relationships between these entities.

JacMIN creates indexSON.

indexSON itself is not the scraper or indexing application.

---

# 12. indexSON Relationship Model

indexSON should be able to represent relationships including:

```text
programme ─── contains ───► course

plan ──────── contains ───► course

course ───── owned by ────► school

school ───── belongs to ──► faculty

programme ── managed by ──► faculty / school

course ───── offered as ──► offering

offering ─── occurs in ───► semester
```

These relationships should support navigation in either direction where useful.

# 21. Automatic and Manual Modes

Each JacSON record must have a clear data-management mode.

Supported modes:

```text
AUTOMATIC
MANUAL
```

---

## 21.1 Automatic mode

Automatic mode means:

> JacMIN-generated values are controlled by the relevant public UQ source and may be updated during future scrapes.

UI indication:

```text
Data mode: ● Automatic
```

Scraping may update this record normally.

---

## 21.2 Manual mode

When an administrator changes managed JacSON data manually, the record should switch to:

```text
Data mode: ● Manual
```

Manual mode means:

> The published JacSON record is controlled by the saved manual version and must not be overwritten by subsequent automatic scrapes.

JacMIN may continue scraping the source in the background so administrators can compare the manual version with current source data.

However, it must not replace the published manual version automatically.

---

# 22. Switching to Manual Mode

When an administrator edits an automatically managed record, JacMIN should make the transition clear.

Example interaction:

```text
This record is currently managed automatically.

Saving these changes will switch this profile to Manual mode.
Future scrapes will not overwrite your manual version.

[Cancel] [Save as Manual]
```

Do not silently change ownership of the record.

---

# 23. Preserve Automatic Source Data During Manual Mode

When a record is switched to Manual mode, JacMIN should preserve:

1. the manual published representation;
2. the latest automatically scraped representation.

Conceptually:

```text
Course profile
│
├── automatic_source
│   └── latest scraped data
│
└── manual_version
    └── published override
```

This enables:

- source comparison;
- detecting changes at UQ;
- restoring automatic behaviour;
- auditability.

---

# 24. Manual Mode Source Comparison

For manually managed profiles, JacMIN should provide:

```text
[ Compare with current UQ data ]
```

The comparison should identify:

- unchanged fields;
- fields changed manually;
- fields subsequently changed at UQ;
- fields existing only in one representation.

Example:

```text
Course title
Manual:    Introduction to Mining
Automatic: Introduction to Mining
           No difference

Course aims
Manual:    [custom text]
Automatic: [new source text]
           Source changed since override
```

This is especially important because a manual record may remain overridden for months while the source profile continues changing.

---

# 25. Returning to Automatic Mode

Administrators must be able to switch a manually controlled profile back to Automatic.

Provide:

```text
[ Return to Automatic ]
```

Before completing the action, JacMIN should show which automatic representation will become active.

Example:

```text
Return MGTS1301-XXXXX-7660 to automatic management?

The current manually edited version will no longer be published.

The latest automatically scraped data from UQ will become active.

Your manual revision history will be retained.

[Cancel] [Return to Automatic]
```

Do not delete manual history.

---

# 26. Manual Override History

Every manual modification must be auditable.

Store:

- profile identifier;
- timestamp;
- administrator identity where available;
- mode before;
- mode after;
- fields changed;
- previous value;
- new value;
- optional reason/comment.

Example:

```json
{
  "profile": "MGTS1301-12345-7660",
  "changed_at": "...",
  "changed_by": "...",
  "reason": "Corrected incorrect published assessment weighting",
  "changes": [
    {
      "field": "assessments[1].weight_percent",
      "from": 30,
      "to": 25
    }
  ]
}
```

This audit information belongs to JacMIN's administrative data store.

It should not necessarily be exposed through the public API.

---

# 27. Manual Override Reason

When entering Manual mode, provide an optional but strongly encouraged field:

```text
Reason for manual override
[________________________________________________]
```

Potential examples:

- known UQ source error;
- temporary correction;
- programme transition;
- parser unable to interpret source;
- emergency content correction.

For organisations that require stricter governance, JacMIN should support making this field mandatory through configuration.

---

# 28. Per-Field Provenance

Although the record has a profile-level Automatic/Manual mode, JacMIN should retain enough internal provenance to determine which fields were manually edited.

This allows the interface to visually distinguish:

```text
Course title
Automatic source

Course aims
Manual modification

Assessment 2 weight
Manual modification
```

This does not require exposing complex provenance through JacSON itself.

It is primarily an administrative function.

---

# 29. Future Partial Override Support

Initial implementation may use profile-level Automatic/Manual control.

However, the internal override model should avoid making future **field-level overrides** impossible.

A future version may allow:

```text
Profile mode: Automatic

Overrides:
✓ assessment[1].weight_percent
✓ course.aims
```

while all other fields remain scraper-controlled.

Do not design the persistence layer in a way that requires a complete rewrite to support this later.

# 31. Manual Creation

JacMIN should support creating a JacSON profile manually when necessary.

Use cases may include:

- source temporarily unavailable;
- source parsing failure;
- testing;
- legacy migration.

Manual creation should require enough identifying information to prevent accidental duplicate profiles.

It should always be marked clearly:

```text
Data mode: Manual
Source status: Manually created
```

# 32. Raw Source Inspection

Where useful for troubleshooting, JacMIN should allow administrators to inspect:

- source URL;
- last scrape date;
- source response status;
- selected raw source data;
- parsing warnings.

Managers should not need this information for ordinary editing, so it should live under an advanced or diagnostic section.

---

# 33. Save Workflow

Manual changes should follow:

```text
EDIT
 ↓
VALIDATE
 ↓
SHOW ERRORS/WARNINGS
 ↓
SAVE MANUAL VERSION
 ↓
REBUILD AFFECTED indexSON
 ↓
STAGE API CHANGE
 ↓
PUBLISH
```

A manual edit must pass the same JacSON schema validation as automatically generated data.

Manual mode is not permission to publish malformed JSON.

---

# 34. Draft vs Published Changes

Where practical, separate saving from publishing.

Possible workflow:

```text
Saved in JacMIN
      ↓
Pending API change
      ↓
[Publish]
```

This lets managers prepare corrections without immediately changing live Blackboard/JacDASH/JacXEL output.

Configuration may optionally permit automatic publishing after validation.

---

# 35. indexSON Regeneration After Manual Changes

If a manual change affects indexable data such as:

- course title;
- school;
- faculty;
- programme relationship;
- semester;
- course identity;

JacMIN must regenerate affected indexSON resources before publication.

Example:

```text
Manual school change
        ↓
update JacSON
        ↓
rebuild:
  /index/courses/MINE3110.json
  /index/schools/old-school.json
  /index/schools/new-school.json
  /index/faculties/...
        ↓
publish atomically
```

The API must not temporarily expose inconsistent JacSON/indexSON relationships.

This protects historical Blackboard sites from future breaking schema changes.

A future JacBLACK authoring tool may default newly created components to the current API version while existing components remain pinned.

# 57. Acceptance Criteria

JacSYS initial production release is complete when:

1. JacMIN can scrape an individual UQ course profile.
2. JacMIN can scrape a teaching period.
3. JacMIN can retrieve programme/catalogue relationships.
4. JacMIN can generate JacSON.
5. JacMIN can generate indexSON.
6. Generated files validate against the API schema.
7. API output is published under an explicit major version.
8. Existing API versions can coexist.
9. A course can be resolved without knowing its JacSON filename.
10. Programme → course relationships are represented.
11. School → course relationships are represented.
12. Faculty → school/course relationships are represented.
13. JacMIN provides course search.
14. Search can filter by key organisational and offering metadata.
15. An administrator can open a course in JacMIN.
16. Every supported JacSON field can be inspected.
17. Every supported JacSON field can be manually edited through an appropriate interface.
18. Editing an Automatic record can explicitly switch it to Manual mode.
19. Manual records are not overwritten by future scrapes.
20. Current automatic source data continues to be retained for comparison.
21. Manual and automatic versions can be compared.
22. A manual record can be returned to Automatic mode.
23. Manual change history is retained.
24. Manual records can be searched/reviewed as a group.
25. Manual data is schema validated before publication.
26. Relevant indexSON files rebuild when manually edited indexed data changes.
27. JacMIN can preview pending API changes.
28. Invalid API output cannot replace valid production data.
29. JacDASH operates entirely from the static API.
30. JacBLACK operates entirely from the static API.
31. JacBLACK can explicitly target an API version.
32. JacMIN is not required to be online for consumers to access published data.
33. UQ Cloud deployment is documented.
34. Raspberry Pi deployment is documented.
35. The architecture remains compatible with future JacXEL development.

# 60. Desired End State

JacSYS should make the following statements true:

> **JacMIN is the administrative source of truth for how the JacSYS static API is created and maintained.**

> **JacSON is the machine-readable representation of individual UQ JAC course profiles.**

> **indexSON is the machine-readable representation of how courses, programmes, schools, faculties, semesters and related entities are grouped and connected.**

> **JacBLACK, JacDASH and JacXEL can independently consume a stable versioned API without understanding how the source information was scraped or administered.**

> **Managers can safely correct or replace automatically scraped JacSON data through JacMIN without directly editing JSON or GitHub files, while retaining the ability to compare against and return to the automatic source.**

> **Existing teaching materials can remain pinned to an older API contract so future schema changes do not break historical Blackboard courses or other integrations.**

These are the primary architectural objectives of JacSYS.
